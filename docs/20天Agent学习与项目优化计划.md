# Sonic / Matter：20 天 Agent 学习与项目优化计划

> 目标：在保留现有音乐创作 Demo 的基础上，把项目升级为一个可规划、可调用工具、可验证、可修订、可审计的游戏音频 Agent，并确保学习者能够独立解释和实现核心机制。

## 1. 20 天结束时要交付什么

### 项目能力

- 一个明确的 `Audio Director Agent`，能够把自然语言音乐修改要求转成结构化计划。
- 至少 5 个由 TypeScript 实现、带 Zod Schema 的确定性工程工具。
- 一条 `plan → execute → validate → revise → approve` 执行链路。
- Agent Run、Step、Tool Call、Validation Report 和 Project Diff 数据模型。
- 可取消、有步骤预算、有修订上限的执行器。
- 前端执行轨迹、约束验收结果和工程修改预览。
- 用户批准前不覆盖原工程，批准后接入现有撤销/重做历史。
- 至少 20 个固定评测案例，以及可重复运行的汇总报告。

### 学习成果

完成后应当能够不用背稿解释：

1. LLM、Tool Calling 和 Agent 的区别。
2. 模型为什么不能直接执行工具。
3. TypeScript 类型与 Zod 运行时校验的区别。
4. Agent 为什么需要状态机、步骤预算、超时和终止条件。
5. 哪些问题适合交给模型，哪些必须用确定性代码处理。
6. 如何判断 Agent 真的完成了任务，而不是只返回了一段看似合理的文字。
7. 如何避免 Prompt Injection、未知工具调用、无限循环和费用失控。
8. 如何用 Trace、评测数据和失败案例证明系统质量。

### 面试材料

- 一张 Agent 架构图。
- 一张状态机图。
- 一张评测指标表。
- 一个成功案例、一个自动修订案例、一个安全失败案例。
- 一段 2–3 分钟演示视频。
- 一份能够解释关键技术决策和取舍的 README。

## 2. 时间和学习方式

建议每天投入 2–3 小时，总投入约 45–55 小时。某一天没有完成时，不要压缩理解和测试时间，可以顺延，不建议同时合并两天的核心任务。

每天采用同一节奏：

| 环节 | 建议时间 | 做什么 |
| --- | ---: | --- |
| 原理学习 | 25–35 分钟 | 理解当天涉及的概念，能够用自己的话复述 |
| 阅读现有代码 | 20–30 分钟 | 找出项目中可以复用的类型、函数和测试模式 |
| 亲手实现 | 60–90 分钟 | 自己完成核心类型、函数或测试，不整段照抄 AI 代码 |
| 测试与调试 | 30–45 分钟 | 运行局部测试，观察成功和失败路径 |
| 复盘与提交 | 15–20 分钟 | 记录今天学到的内容，运行验证并创建独立 commit |

## 3. 你和 AI 的协作边界

### 你亲手完成

- 核心数据模型的第一版。
- 状态转换表和终止条件。
- 至少前三个工具的主要实现。
- 前 5 个评测案例。
- 每个阶段的技术复盘。
- 面试中需要讲解的技术决策。

### AI 适合协助

- 解释陌生代码和错误信息。
- 对设计方案提出边界情况和反例。
- Review 你写的类型、状态机、工具与测试。
- 补充重复性测试、错误文案和文档。
- 帮助定位失败原因，但不直接替你隐藏问题。
- 在你理解后处理机械性的文件拆分或重构。

### 每次使用 AI 前先回答

1. 我认为问题发生在哪一层？
2. 我期望输入和输出分别是什么？
3. 我准备如何验证它是否正确？

如果不能回答，先缩小问题，不直接要求 AI “把整个功能做完”。

## 4. 目标架构

```text
用户需求 + 当前 Project
          │
          ▼
   Requirement Parser
          │ 结构化约束
          ▼
       Planner
          │ AgentPlan
          ▼
   Tool Runner / Registry ───────┐
          │ Project Snapshot     │
          ▼                      │
      Evaluator                  │
       │      │                  │
    通过      失败               │
       │      └── Revision Plan ─┘
       ▼
 Project Diff + Approval
       │
       ▼
现有 History / Undo / Redo
```

设计原则：模型负责理解、规划和选择；普通代码负责执行、验证、权限、限额和数据一致性。

## 5. 20 天执行计划

## 第 1 天：建立项目地图和基线

### 学习

- 前端、后端、模型调用、Project 数据和音频导出的边界。
- 一次请求如何从 React 经过 API 到达 Agent 服务。
- 单次 LLM 调用与 Agent 系统的差别。

### 动手

- 阅读 `web/src/App.tsx`、`web/src/project/model.ts`、`server/src/index.ts`。
- 画出现有“用户请求 → Agent → Project → 前端应用”的数据流。
- 记录当前 Agent 能做什么、不能做什么。
- 运行一次完整 `npm run verify`，记录基线测试数量和构建结果。

### 验收

- 能在 3 分钟内讲清当前系统的数据流。
- 能指出至少 3 个现在只是“模型调用”而不是“Agent 闭环”的地方。

### 产出

- `docs/agent/00-current-architecture.md`
- 建议 commit：`文档：梳理现有 Agent 数据流与升级边界`

## 第 2 天：TypeScript 类型与运行时 Schema

### 学习

- 联合类型、泛型、类型收窄和不可变数据。
- TypeScript 类型只在编译期存在，Zod 在运行时保护边界。
- 为什么模型输出和 HTTP 输入都不能仅靠类型声明。

### 动手

- 定义 `AgentRunStatus`、`AgentRun`、`AgentStep`、`ToolCall`。
- 为字符串长度、步骤数量和结果摘要设置限制。
- 编写对应 Zod Schema。
- 为正常、缺字段、越界和未知字段编写测试。

### 验收

- 能解释 `type AgentRun` 与 `AgentRunSchema` 为什么都需要。
- 非法 Run 无法通过 Schema。

### 产出

- `server/src/agent/types.ts`
- `server/src/agent/types.test.ts`
- 建议 commit：`功能：建立 Agent 运行记录与校验模型`

## 第 3 天：状态机和终止条件

### 学习

- 状态、事件和状态转换。
- 终止状态、最大步骤、最大修订次数和循环检测。
- 为什么不能用一堆互相独立的布尔值表示 Agent 状态。

### 动手

- 画出 `planning → executing → validating → revising → awaiting_approval` 状态图。
- 实现纯函数 `transitionRun(current, event)`。
- 对所有合法转换和关键非法转换编写表驱动测试。
- 定义失败、取消和完成后的行为。

### 验收

- `completed`、`failed`、`canceled` 不能重新进入执行状态。
- 非法转换得到稳定错误，而不是静默跳转。

### 产出

- `server/src/agent/stateMachine.ts`
- `server/src/agent/stateMachine.test.ts`
- 建议 commit：`功能：用状态机约束 Agent 执行生命周期`

## 第 4 天：Tool Calling 原理和工具契约

### 学习

- 模型只产生工具调用请求，真正执行工具的是应用程序。
- 工具白名单、输入 Schema、输出 Schema 和错误分类。
- 确定性逻辑与概率性模型的职责分界。

### 动手

- 设计 `AgentTool<Input, Output>` 泛型接口。
- 实现 Tool Registry 的注册、查询和重复名称检查。
- 定义未知工具、参数无效、执行失败和取消错误。
- 只使用假的示例工具验证调用过程，暂不接业务代码。

### 验收

- 未注册工具无法执行。
- 工具参数必须经过 Schema 才能进入执行函数。
- 工具执行结果具有统一结构。

### 产出

- `server/src/agent/toolRegistry.ts`
- `server/src/agent/toolRegistry.test.ts`
- 建议 commit：`功能：建立带 Schema 的 Agent 工具注册表`

## 第 5 天：第一个只读工具

### 学习

- 纯函数、副作用与不可变快照。
- 为什么只读工具适合成为工具系统的第一个真实能力。
- 如何把复杂 Project 压缩成模型需要的最小上下文。

### 动手

- 实现 `inspect_project`。
- 输出工程时长、速度、调式、轨道摘要、音符数量和乐器列表。
- 不返回不必要的完整音符数组。
- 添加 Project 为空、老版本工程和异常数据测试。

### 验收

- 相同 Project 输入得到相同摘要。
- 工具不会修改原始 Project。
- 摘要足以支持后续规划，但不会无意义占用大量 Token。

### 产出

- 第一个真实工具和测试。
- 建议 commit：`功能：增加工程检查 Agent 工具`

### 里程碑 A

此时应当能独立解释：Schema、状态机、工具注册表和工具执行之间的关系。

## 第 6 天：轨道修改工具

### 学习

- 命令式修改与返回新快照的区别。
- 业务不变量：不能删除最后一条轨道、ID 不能冲突、音量必须有界。

### 动手

- 封装 `add_track`、`update_track`、`remove_track`。
- 优先复用 `web/src/project/tracks.ts` 中的确定性逻辑；如需共享代码，先设计共享边界，不直接复制两份。
- 为每个工具编写成功和失败测试。

### 验收

- 工具不会原地修改 Project。
- 所有现有轨道业务规则仍然生效。
- 错误结果可被 Runner 判断是否应该终止。

### 产出

- 三个轨道工具和测试。
- 建议 commit：`功能：开放受约束的轨道编辑工具`

## 第 7 天：音符修改与工程验证工具

### 学习

- 数值钳制与拒绝非法输入的取舍。
- 输入验证、业务验证和最终验收的区别。

### 动手

- 实现 `replace_track_notes`。
- 实现 `validate_project`。
- 检查音高、起点、时长、力度、工程边界和最大音符数量。
- 为恶意超长数组、NaN、越界音符和错误轨道类型编写测试。

### 验收

- 工具结果始终可以通过现有 Project Schema。
- 非法输入不能产生部分修改。

### 产出

- 音符工具、工程验证工具和测试。
- 建议 commit：`功能：增加音符编辑与工程验证工具`

## 第 8 天：Planner 与 Structured Output

### 学习

- System Prompt、用户需求和工具描述的作用。
- Structured Output 与“请输出 JSON”的区别。
- 计划、执行参数和验收条件为什么应当分开。

### 动手

- 定义 `AgentPlan`：目标、约束、步骤、验收条件。
- 实现 Planner 的模型输出 Schema。
- 限制计划步骤只能引用注册工具。
- 增加无 Agent Key 时的固定本地计划，保证离线测试。
- 使用模拟模型测试非法 JSON、未知工具和超长计划。

### 验收

- Planner 不执行任何工程修改。
- 无效计划不会进入 Runner。
- 能区分“用户目标”和“程序可检查约束”。

### 产出

- `server/src/agent/planner.ts`
- Planner 测试。
- 建议 commit：`功能：生成可校验的 Agent 执行计划`

## 第 9 天：实现最小执行循环

### 学习

- Agent Loop 的上下文更新方式。
- 每一步为何要保存工具结果。
- 最大步骤数、超时和 AbortSignal。

### 动手

- 实现 `plan → execute tools` 的最小 Runner。
- 每次调用前检查状态、步骤预算和取消信号。
- 记录工具名、参数摘要、结果摘要、耗时和错误码。
- 对工具失败、超时、取消和达到步数上限编写测试。

### 验收

- Runner 不会无限循环。
- 取消后不再启动新工具。
- 一次工具错误不会留下无法解释的半成品状态。

### 产出

- `server/src/agent/runner.ts`
- Runner 测试。
- 建议 commit：`功能：实现受预算控制的 Agent 工具执行器`

## 第 10 天：Trace 与最小持久化

### 学习

- Trace、日志和数据库记录的区别。
- 为什么不能记录 API Key、完整供应商错误和隐藏思维链。
- SQLite 事务与原子写入的基本概念。

### 动手

- 将 Run、Step 和 Tool Call 写入独立 SQLite Store。
- 保存可审计摘要，不保存敏感 Prompt 或密钥。
- 支持创建、更新和按 ID 查询 Run。
- 第一阶段只要求保存 Trace，不要求服务重启后继续未完成任务。

### 验收

- 服务重启后仍能查询已完成 Run。
- 数据库和响应中没有密钥或 Authorization 信息。
- 同一步骤更新不会生成重复 Tool Call。

### 产出

- `server/src/agent/runStore.ts`
- Store 测试。
- 建议 commit：`功能：持久化 Agent 执行轨迹`

### 里程碑 B

此时应能从命令行或测试中完成“生成计划并调用真实工程工具”，并查看完整 Trace。

## 第 11 天：确定性 Evaluator

### 学习

- “模型认为完成”与“程序证明完成”的区别。
- 规则评测、模型评测和人工评测各自适合什么问题。

### 动手

- 定义结构化约束：必需乐器、禁用乐器、时长范围、轨道数量和段落音符密度。
- 实现确定性 Evaluator。
- 输出每条规则的通过状态、实际值和原因。
- 不让 LLM 自己给自己的结果打最终分。

### 验收

- 故意违反约束时能准确指出失败项。
- 相同工程和约束得到相同报告。

### 产出

- `server/src/agent/evaluator.ts`
- Evaluator 测试。
- 建议 commit：`功能：用确定性规则验收 Agent 工程结果`

## 第 12 天：自动修订闭环

### 学习

- 反馈闭环与无限自我修订的风险。
- 为什么修订输入应当是结构化失败报告，而不是模糊的“再试一次”。

### 动手

- 将 Validation Report 传回 Planner 生成 Revision Plan。
- 限制最多两轮修订。
- 保存每轮计划、工具调用和验收报告。
- 增加修订成功、修订失败和达到上限测试。

### 验收

- Agent 能修复至少一种可修复约束违规。
- 无法完成时明确进入失败状态，不伪装成功。
- 修订不会重复执行已经成功的无关步骤。

### 产出

- 完整 `plan → execute → validate → revise` 闭环。
- 建议 commit：`功能：根据验收失败自动修订 Agent 计划`

## 第 13 天：设计并接入 Run API

### 学习

- 创建资源、查询资源、取消操作和批准操作的 HTTP 语义。
- 幂等性与重复点击问题。
- 前后端共享契约的版本风险。

### 动手

- 与队友确认新增接口，再实现创建、查询、取消、批准和拒绝 Run。
- 所有错误继续使用统一错误信封。
- 重复批准不能重复修改工程。
- 为完整接口流程编写集成测试。

### 验收

- 只通过 HTTP 请求即可完成一次 Run。
- 访客权限、非法 ID、重复批准和取消终态都有明确行为。

### 产出

- Agent Run 路由及集成测试。
- 建议 commit：`功能：提供 Agent 运行与审批接口`

## 第 14 天：前端 Agent Trace 面板

### 学习

- 服务端状态与前端展示状态的区别。
- 轮询、取消和组件卸载时清理异步任务。
- 为什么不应该展示模型隐藏思维链。

### 动手

- 展示 Run 当前状态、目标、约束和步骤。
- 展示工具名称、成功/失败、耗时和安全摘要。
- 提供取消按钮。
- 对空状态、运行中、失败和终态设计清晰 UI。

### 验收

- 用户可以看懂 Agent 正在做什么。
- 页面卸载后不会继续无意义轮询。
- UI 不展示密钥、完整 Prompt 或内部异常堆栈。

### 产出

- 独立 Trace 组件及状态逻辑测试。
- 建议 commit：`功能：展示 Agent 执行轨迹与取消状态`

## 第 15 天：Project Diff、批准与撤销

### 学习

- 快照 Diff 与文本 Diff 的差别。
- Human-in-the-loop 为什么是控制边界，而不仅是一个确认框。

### 动手

- 计算新增、删除和修改的轨道及音符数量。
- 展示约束验收报告和修订次数。
- 增加批准、拒绝操作。
- 批准后接入现有 Project History，确保可以撤销。
- 拒绝后保持原工程引用和内容不变。

### 验收

- Agent 在批准前不能覆盖用户工程。
- 批准后一次撤销能回到执行前状态。
- 重复点击批准不会重复应用。

### 产出

- Diff 面板与审批流程。
- 建议 commit：`功能：审阅并安全应用 Agent 工程修改`

### 里程碑 C

此时应当能够在浏览器完整演示：输入要求、查看计划、观察工具调用、自动验收、查看 Diff、批准并撤销。

## 第 16 天：建立 20 个评测案例

### 学习

- 单元测试与 Agent Eval 的区别。
- 固定数据集、可重复性和回归比较。

### 动手

- 亲手写前 5 个案例。
- 扩展为：5 个基础创建、5 个修改、5 个带约束、3 个冲突需求、2 个恶意输入。
- 每个案例明确输入工程、用户指令、期望约束和允许的工具。
- 固定不依赖真实付费服务的离线评测模式。

### 验收

- 每个案例都有机器可检查的成功条件。
- 不使用“结果听起来不错”作为唯一标准。

### 产出

- `server/src/agent/evals/cases.ts`
- 建议 commit：`测试：建立 Agent 工程任务评测集`

## 第 17 天：评测 Runner 和报告

### 学习

- 约束满足率、工具成功率、一次完成率和修订成功率。
- 平均数不能掩盖失败分布。
- 质量、延迟、步骤数和成本之间的权衡。

### 动手

- 实现一条命令运行全部 Eval。
- 输出 JSON 原始结果和 Markdown 汇总表。
- 统计成功率、平均步骤、修订次数、耗时和可导出率。
- 保存失败案例摘要，方便回归分析。

### 验收

- 同一固定模型/本地模式下可重复运行。
- 报告能直接指出最常见失败类型。
- README 中的数字可以由脚本重新生成，而不是手填。

### 产出

- Eval Runner、报告生成器和第一份基线报告。
- 建议 commit：`测试：自动运行并汇总 Agent 任务评测`

## 第 18 天：安全与故障演练

### 学习

- Prompt Injection、工具越权、参数攻击和资源耗尽。
- 超时、取消、上游异常和部分失败。
- 最小权限和安全失败原则。

### 动手

- 测试用户要求 Agent 忽略规则、调用不存在工具或执行 Shell。
- 测试超长参数、无限重复步骤、供应商超时和取消。
- 检查日志、Trace、数据库和错误响应是否泄漏敏感内容。
- 编写一份威胁模型和已知限制。

### 验收

- Agent 只能调用白名单工具。
- 达到预算或超时时安全终止。
- 恶意输入不能获得文件、Shell 或任意网络权限。

### 产出

- 安全回归测试。
- `docs/agent/security.md`
- 建议 commit：`安全：限制 Agent 工具权限与资源消耗`

## 第 19 天：架构文档和演示材料

### 学习

- 如何用问题、决策、证据和取舍讲项目，而不是罗列技术栈。
- 如何讲失败案例体现工程判断。

### 动手

- 更新 README 首屏定位。
- 绘制系统架构图和状态机图。
- 整理成功、自动修订、安全失败三个案例。
- 把 Eval 基线结果加入 README。
- 准备 2–3 分钟演示脚本。

### 验收

- 新读者 5 分钟内能理解 Agent 的目标、执行方式和评测结果。
- 所有指标都有可重复生成的来源。
- 文档明确写出没有选择多 Agent 的原因。

### 产出

- README、架构图、案例说明和演示脚本。
- 建议 commit：`文档：补充 Agent 架构评测与演示案例`

## 第 20 天：最终验收与模拟面试

### 学习

- 如何回答架构选择、失败恢复、评测可信度和安全边界问题。
- 如何承认限制，同时给出合理的下一阶段方案。

### 动手

- 从干净依赖环境运行完整验证。
- 运行 Agent Eval 并保存最终报告。
- 手动走通三个演示案例。
- 录制演示视频。
- 进行一次 30 分钟模拟面试并记录回答不清楚的问题。

### 验收

- `npm run verify` 全部通过。
- 至少 20 个 Eval 可一键运行。
- 核心约束满足率达到基线后设定的目标；建议目标不低于 85%。
- Agent 不会无限循环，用户批准前不会覆盖工程。
- Git 工作区干净，每项功能都有对应 commit。

### 产出

- 最终评测报告、演示视频和面试问答清单。
- 建议 commit：`文档：完成 Agent 项目最终验收与面试交付`

## 6. 每 5 天一次学习检查

### 第 5 天

- 能否解释类型校验、状态机和工具注册表？
- 能否不看答案写出一个只读工具？

### 第 10 天

- 能否手写一个有步数上限的 Tool Calling 循环？
- 能否解释 Trace 为什么不能等同于模型思维链？

### 第 15 天

- 能否完整解释计划、执行、验收、修订和人工批准？
- 能否证明批准前原工程没有被修改？

### 第 20 天

- 能否用评测数据说明系统比单次生成更可靠？
- 能否解释最严重的三个风险和对应防护？

如果某个检查点答不清楚，先补原理和小练习，不急着继续增加功能。

## 8. 第一阶段明确不做

为了保证 20 天内完成，以下内容放到下一阶段：

- 多 Agent 角色协作。
- 向量数据库和长期语义记忆。
- 服务重启后自动恢复正在执行的 Run。
- 大规模多模型路由。
- 真实付费服务的自动评测。
- 移动端整体视觉重构。
- 商业级账户注册和多租户权限系统。
- 自动音乐审美评分模型。

如果核心闭环尚未稳定，不因这些功能看起来“更像 AI”而提前加入。

## 9. 面试时的项目主线

建议用下面的逻辑讲项目：

1. 原项目已经能用 LLM 生成结构化音乐工程，但单次调用无法证明结果满足需求。
2. 因此将系统拆成 Planner、受约束工具、状态机 Runner 和确定性 Evaluator。
3. 模型负责理解和规划，程序负责执行、校验、权限和资源控制。
4. 验收失败后最多自动修订两轮，避免无限循环与费用失控。
5. 所有修改先形成 Project Diff，由用户批准后才进入现有撤销历史。
6. 最终通过固定 Eval 集衡量约束满足率、工具成功率、修订率、延迟和成本。

这条主线比“接入了哪些模型”更能体现 Agent 工程能力。

## 10. 如何开始

开始某一天时，可以直接发送：

```text
开始第 1 天。先检查我的理解，不要直接替我完成核心代码。
```

当天协作顺序固定为：概念检查 → 阅读相关代码 → 你写第一版 → AI Review → 补测试 → 完整验证 → commit → 复盘。这样既能持续推进项目，也能确保核心知识真正由你掌握。
