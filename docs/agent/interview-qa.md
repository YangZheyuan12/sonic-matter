# Audio Director Agent：30 分钟模拟面试问答

这份清单按 30 分钟组织。回答时先给结论，再给代码或 Eval 证据，最后主动说明限制；不要把技术栈列表当成架构回答。

## 0–5 分钟：项目主线

### 1. 这个项目解决什么问题？

原项目能让 LLM 生成结构化音乐工程，但一次模型调用不能证明结果满足需求，也不能安全处理失败。现在将它改造成 Audio Director Agent：模型负责理解和规划，普通代码负责工具执行、约束验收、资源限制和数据一致性，所有改动先形成候选快照，用户批准后才应用。

### 2. 为什么不是直接让模型返回完整 Project JSON？

完整 JSON 一次生成难以定位局部错误，也不能说明做过哪些修改。白名单工具把变化限制在明确操作内，Trace 可以记录工具、耗时和结果；Evaluator 还能针对具体约束反馈并触发最小修订。

### 3. 为什么没有使用多 Agent？

当前所有阶段共享一个 Project，Planner、Runner 和 Evaluator 已有确定接口，没有必须并行自治的子任务。多 Agent 会增加状态同步、仲裁、调用成本和延迟，而当前 Eval 没有证明它能提高成功率。因此先保留单 Agent，未来必须用对照数据证明角色拆分有收益才引入。

## 5–12 分钟：架构与状态

### 4. 一次请求怎样流过系统？

输入先做安全与冲突检查，Planner 生成受 Schema 和工具注册表约束的计划，Runner 在候选快照上执行工具，Evaluator 做确定性验收；失败且仍有预算时进入 Revision，通过后停在 `awaiting_approval`。用户批准才进入 `completed` 并写入前端 History，拒绝则进入 `canceled`。

### 5. 状态机解决了什么问题？

它把“正在规划”“正在执行”“验证失败待修订”和“已验证但未批准”区分开，禁止非法跳转和终态复活。这样 API、存储和前端不会各自猜测运行阶段，也能明确恢复或取消边界。

### 6. 如何保证 Agent 不会无限循环？

Planner 的计划最多 8 步，Revision 最多 2 轮；Runner 会同时检查计划长度和实际执行步数。达到上限后返回明确错误，例如 `revision_limit_reached`，测试会构造无效修订证明第三轮不会发生。

### 7. 服务中途崩溃怎么办？

Run、Trace 和候选数据会持久化，但当前版本不会在重启后自动续跑，这是明确限制。合理的下一步是为执行轮次增加租约和幂等键，启动时只恢复租约过期且可安全重放的步骤；在此之前宁可把中断 Run 标记失败，也不重复修改。

## 12–19 分钟：评测可信度与失败恢复

### 8. 20/20 是否说明 Agent 已经完全可靠？

不是。20/20 来自固定离线适配器，证明控制流程和断言可重复，不代表真实模型面对任意表达都正确。报告同时给出适配器、付费调用数、一次完成率、修订率和失败分布，避免只展示一个总分。

### 9. 怎样证明闭环比单次生成更可靠？

当前候选任务一次完成率是 93.33%，`modify-02-change-instrument` 首轮没有满足 Cello 约束，Evaluator 反馈后第二轮修复，修订样本成功率为 100%。这证明闭环挽回了固定集中的一个首轮失败。更强结论还需要真实模型多轮 A/B、固定参数和统计置信区间。

### 10. Evaluator 为什么不用另一个模型？

轨道数量、必需乐器、禁用乐器、段落密度、Schema 合法性和音符边界都能由普通代码确定判断。用模型验收会引入随机性和额外成本，也可能让规划模型与裁判共享同一种偏差。审美质量暂未自动评分，不能假装确定性规则覆盖了主观音乐质量。

### 11. 自动修订失败时怎样处理？

达到两轮上限、无法生成合法修订计划或工具失败时，Run 明确进入 `failed`，保留 Trace 和错误代码，不把候选伪装成成功，也不覆盖当前工程。用户可以根据失败原因改写需求或手动编辑。

## 19–25 分钟：安全与人工控制

### 12. 最严重的三个风险是什么？

第一是提示词注入和越权，靠前置安全策略、工具注册表、Schema 与脱敏处理；第二是错误候选覆盖工程，靠候选快照、确定性验收、Diff、人工批准与撤销；第三是循环和资源失控，靠步骤、修订、超时、并发及用量上限。

### 13. 工具白名单是否已经足够安全？

不够。白名单限制了能力范围，但合法工具仍可能收到恶意或超大参数，所以每个工具还需要输入 Schema、业务边界和输出校验。服务端也必须独立做身份、来源、频率和并发检查，不能信任 Planner 或前端。

### 14. Trace 是模型思维链吗？

不是。Trace 只记录可审计的业务事件，例如计划摘要、工具名、参数摘要、执行结果、验收规则和状态迁移。它不保存也不展示模型隐藏推理；这样既满足排障需求，也减少敏感信息泄露。

### 15. 如何证明批准前原工程没有被修改？

Runner 接收源快照并产生独立候选快照，Review 只比较两者。前端只有收到批准结果后才通过 `pushHistory` 应用候选，同一 Run 还只能领取一次应用权；测试证明批准前源引用不变、批准后只有一个历史步骤，撤销可回到原引用。

## 25–30 分钟：限制和下一步

### 16. 如果再给两周，优先做什么？

先做真实模型对照评测，确认离线结论能否外推；再实现 Run 幂等恢复，扩大安全攻击语料，最后研究音乐质量评价。不会优先增加多 Agent，因为目前最缺的是外部有效性和恢复能力，而不是角色数量。

### 17. 当前最容易被追问、还需要补强的地方是什么？

1. **“闭环一定优于单次生成吗？”** 当前只有固定集中的一个修订样本，回答必须限定证据范围；下一步做真实模型 A/B。
2. **“服务重启为何不能续跑？”** 当前缺少步骤租约和完整幂等协议；不能只说数据库已持久化就等于可恢复。
3. **“音乐好不好听怎样评？”** 当前只验证结构和可导出性；主观质量仍需盲听、人类偏好或专门评价模型。

这三个问题如果回答成“已经完全解决”，反而说明没有理解系统边界。合格回答应当指出现有证据、不能推出的结论，以及下一步可验证的方案。
