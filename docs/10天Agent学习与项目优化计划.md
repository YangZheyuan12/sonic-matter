# Sonic / Matter：10 天 Agent 学习与项目优化冲刺计划

> 适合时间：连续 10 天，每天约 3–4 小时，总投入约 35–45 小时。
>
> 核心目标：把现有“调用模型生成 Project JSON”的流程，升级成一个可规划、可调用工具、可验证、可修订、可审阅的 Audio Director Agent；同时确保学习者能独立解释关键原理。

完整版学习路径见 [`20天Agent学习与项目优化计划.md`](./20天Agent学习与项目优化计划.md)。本计划是压缩后的求职冲刺版，不是把 20 天任务机械地塞进 10 天。

## 1. 十天后要达到的效果

用户输入：

```text
把后半段做得更紧张，增加低音轨，但不要使用鼓组，工程保持在 30 秒以内。
```

系统能够：

1. 把自然语言整理成目标和程序可检查的约束。
2. 生成结构化执行计划。
3. 调用白名单中的音乐工程工具。
4. 记录计划、步骤、工具结果、耗时和错误。
5. 用确定性规则检查禁用乐器、时长、轨道和音符边界。
6. 验收失败后最多自动修订一次。
7. 展示工程修改 Diff。
8. 用户批准后才应用修改，并可通过现有历史功能撤销。
9. 使用至少 20 个固定案例重复评测约束满足率和工具成功率。

## 2. 冲刺范围

### 必须完成

- Agent Run、Step、Tool Call、Plan、Validation Report 数据模型。
- 状态机和最大步骤、超时、取消、最大修订次数。
- 至少 5 个带 Zod Schema 的真实工程工具。
- `plan → execute → validate → revise → approve` 闭环。
- Agent Run API。
- 前端 Trace、Diff、批准和拒绝。
- 20 个离线 Eval 案例和一份汇总报告。
- 架构图、案例、README 和演示脚本。

### 十天内不做

- 多 Agent 协作。
- 向量数据库和长期记忆。
- 服务重启后恢复正在执行的任务。
- 自动调用真实付费音乐或音效服务做评测。
- 移动端整体重构。
- 商业级注册和多租户权限系统。
- 用另一个 LLM 作为唯一验收者。

## 3. 每天的固定节奏

| 环节 | 时间 | 要求 |
| --- | ---: | --- |
| 原理学习 | 30–40 分钟 | 能用自己的话复述，不只看代码 |
| 阅读现有实现 | 20–30 分钟 | 找到可以复用的项目逻辑 |
| 亲手实现 | 90–120 分钟 | 核心类型和函数由自己写第一版 |
| 测试与调试 | 40–60 分钟 | 同时验证成功和失败路径 |
| 复盘与提交 | 20 分钟 | 完整验证、独立 commit、记录疑问 |

如果每天只能投入 1–2 小时，建议把本计划延长到 14 天，不要通过跳过测试和复盘压缩时间。

## 4. 你与 AI 的分工

### 你负责

- 画出数据流和状态机。
- 编写核心类型的第一版。
- 实现状态转换函数。
- 实现前三个真实工具。
- 亲手写前 5 个 Eval 案例。
- 总结技术取舍和失败原因。

### AI 协助

- 讲解相关现有代码。
- Review 设计并补充边界情况。
- 提供小型示例，而不是一次生成整个系统。
- 补充重复性测试和错误处理。
- 协助定位测试失败和整理评测报告。

每天开始时可以发送：

```text
开始 10 天冲刺的第 N 天。先检查我的理解，不要直接替我完成核心代码。
```

## 5. 十天执行安排

## 第 1 天：理解现有系统并确定 Agent 边界

### 学习重点

- LLM 调用、Tool Calling 和 Agent 的区别。
- 当前 React、Express、Project Schema 和模型调用的数据流。
- 为什么 Agent 不等于“连续调用几次模型”。

### 项目任务

- 阅读 `web/src/App.tsx`、`web/src/project/model.ts`、`server/src/index.ts`。
- 画出现有流程和目标流程两张图。
- 定义唯一核心场景：自然语言修改当前音乐工程。
- 确定限制：最多 8 个工具调用、最多 1 次修订、总超时 90 秒。
- 运行 `npm run verify`，记录测试和构建基线。

### 你需要能回答

- 现在的 `/api/project/edit` 为什么仍然更接近单次生成？
- 模型、工具执行器和验证器分别负责什么？
- 哪些音乐规则必须由普通代码检查？

### 当天产出

- 当前架构图和目标架构图。
- Agent 范围与非目标说明。
- 建议 commit：`文档：明确 Audio Director Agent 架构与边界`

## 第 2 天：数据模型、Zod 与状态机

### 学习重点

- TypeScript 联合类型、类型收窄和不可变数据。
- TypeScript 编译期类型与 Zod 运行时校验的区别。
- 有限状态机、终止状态和非法转换。

### 项目任务

- 定义 `AgentRunStatus`、`AgentRun`、`AgentStep`、`ToolCall`。
- 定义 `AgentPlan`、`ValidationReport`、`ProjectDiff`。
- 编写对应 Zod Schema，限制长度、步骤数和数组数量。
- 实现 `transitionRun(current, event)` 纯函数。
- 为合法和非法转换编写表驱动测试。

### 你需要能回答

- 为什么有 TypeScript 类型后还需要 Zod？
- 为什么不用 `isLoading`、`isFailed` 等多个布尔值表示状态？
- `completed` 之后为什么不能重新进入 `executing`？

### 当天验收

- 非法 Run 无法通过 Schema。
- 终态不能重新进入执行状态。
- 状态转换逻辑不依赖 Express 或数据库。

### 建议 commit

`功能：建立 Agent 数据模型与生命周期状态机`

## 第 3 天：工具注册表和 5 个工程工具

### 学习重点

- 模型只请求调用工具，应用程序才真正执行工具。
- 工具白名单、输入 Schema、输出 Schema 和统一错误。
- 纯函数、不可变 Project 快照和业务不变量。

### 项目任务

- 定义 `AgentTool<Input, Output>`。
- 实现 Tool Registry 和未知工具拒绝机制。
- 实现至少 5 个工具：
  - `inspect_project`
  - `add_track`
  - `update_track`
  - `replace_track_notes`
  - `validate_project`
- 优先复用现有轨道、音符和 Project 逻辑，不复制两份规则。
- 测试未知工具、参数越界、取消和原始 Project 不被修改。

### 你需要能回答

- 为什么不能让模型生成 JavaScript 后直接执行？
- 为什么 `inspect_project` 不应该返回所有音符的完整 JSON？
- 工具输入验证和最终结果验收有什么区别？

### 当天验收

- 每个工具都能脱离模型独立测试。
- 相同输入产生相同结果。
- 模型无法调用注册表以外的能力。

### 建议 commit

`功能：建立白名单工具注册表与音乐工程工具`

## 第 4 天：Planner 和 Structured Output

### 学习重点

- Structured Output 与在 Prompt 里要求 JSON 的区别。
- 目标、约束、执行步骤和验收条件为什么要分开。
- 模型输出为何必须二次校验。

### 项目任务

- 定义 Planner 输入和输出 Schema。
- 从用户需求提取必需乐器、禁用乐器、时长和段落密度等约束。
- 生成只引用注册工具的 `AgentPlan`。
- 拒绝未知工具、超长计划和不可识别约束。
- 增加本地固定 Planner，保证无 API Key 时可演示和测试。
- 使用模拟模型测试非法 JSON 和错误计划。

### 你需要能回答

- Planner 为什么不能直接修改 Project？
- “后半段更紧张”如何转成程序可以检查的指标？
- 为什么本地固定 Planner 对测试很重要？

### 当天验收

- Planner 输出能够直接交给 Runner。
- 无效计划不会进入工具执行阶段。
- 计划中包含明确、可验证的成功条件。

### 建议 commit

`功能：生成带约束和验收条件的 Agent 计划`

## 第 5 天：Runner、预算、超时和 Trace

### 学习重点

- Agent Loop 如何更新上下文。
- 最大步骤、超时、取消和循环检测。
- Trace 与日志、隐藏思维链的区别。

### 项目任务

- 实现 `plan → execute tools` 执行循环。
- 每次工具调用前检查状态、步骤预算和 `AbortSignal`。
- 记录工具名、参数摘要、结果摘要、耗时和错误码。
- 不记录 API Key、Authorization、完整 Prompt 或模型隐藏思维链。
- 添加成功、工具失败、超时、取消和达到步数上限测试。
- 需要保存历史 Trace 时使用最小 SQLite Store；不实现运行中任务恢复。

### 你需要能回答

- 为什么必须限制最大工具调用次数？
- 用户取消后，系统还允许启动新工具吗？
- Trace 中应该展示什么，不应该展示什么？

### 当天验收

- Runner 不会无限执行。
- 取消和超时都进入明确终态。
- 失败 Run 仍保留足够的可审计信息。

### 建议 commit

`功能：实现有预算可取消的 Agent 执行器`

### 中期检查

完成第 5 天后，应当能不看代码画出：

```text
用户需求 → Planner → Tool Registry → Runner → Project Snapshot
```

并能从命令行或测试完成一次不带 UI 的 Agent 运行。

## 第 6 天：Evaluator 与一次自动修订

### 学习重点

- “模型说完成”与“程序证明完成”的区别。
- 确定性评测、LLM-as-a-Judge 和人工评测的适用范围。
- 反馈闭环为什么需要修订上限。

### 项目任务

- 实现规则：Project Schema、工程时长、必需/禁用乐器、音符边界、轨道数量和后半段音符密度。
- 生成逐条约束的结构化 Validation Report。
- 验收失败时把失败报告交给 Planner 生成 Revision Plan。
- 最多允许 1 次自动修订。
- 测试修订成功、修订仍失败和不可修复要求。

### 你需要能回答

- 为什么不能问同一个模型“你刚才做对了吗”作为唯一验收？
- 哪些音乐质量暂时无法用确定性规则评价？
- 为什么修订输入应该是结构化失败报告？

### 当天验收

- 至少一种违反约束的结果能够被自动修复。
- 无法满足要求时明确失败，不伪装成功。
- 修订不会超过限制。

### 建议 commit

`功能：验收并有限修订 Agent 工程结果`

## 第 7 天：Agent Run API

### 学习重点

- REST 资源、HTTP 状态码和统一错误信封。
- 幂等性和重复点击。
- 前后端共享契约的变更风险。

### 项目任务

- 按仓库约定先与队友确认共享接口变更。
- 实现：
  - `POST /api/agent/runs`
  - `GET /api/agent/runs/:id`
  - `POST /api/agent/runs/:id/cancel`
  - `POST /api/agent/runs/:id/approve`
  - `POST /api/agent/runs/:id/reject`
- 重复批准不能重复应用修改。
- 所有错误继续使用现有错误信封。
- 编写从创建到批准的完整接口测试。

### 你需要能回答

- 为什么创建和批准使用 `POST`？
- 什么是幂等性，为什么批准操作必须考虑它？
- 为什么 API 响应不能返回内部 Prompt 和供应商原始错误？

### 当天验收

- 只使用 HTTP 即可完成一次完整 Run。
- 非法 ID、重复批准和取消终态都有稳定行为。
- 现有接口测试不回归。

### 建议 commit

`功能：提供 Agent 运行查询取消与审批接口`

## 第 8 天：前端 Trace、Diff 和人工批准

### 学习重点

- 服务端状态和 React UI 状态的区别。
- 轮询、取消、组件清理和错误展示。
- Human-in-the-loop 为什么是安全控制边界。

### 项目任务

- 展示 Agent 目标、约束、状态和步骤。
- 展示工具名称、状态、耗时和安全摘要。
- 计算轨道、音符、时长变化的 Project Diff。
- 增加取消、批准和拒绝按钮。
- 用户批准前不替换当前 Project。
- 批准后接入现有 History，确保一次撤销可以返回执行前状态。

### 你需要能回答

- 为什么不能 Agent 执行结束就自动覆盖工程？
- Project Diff 与文本 JSON Diff 有什么区别？
- 页面卸载后轮询和异步任务应如何处理？

### 当天验收

- 用户能看懂 Agent 做了什么。
- 拒绝后原工程内容保持不变。
- 批准后可以撤销。
- UI 不展示敏感信息和隐藏思维链。

### 建议 commit

`功能：审阅 Agent 轨迹与工程修改后再应用`

## 第 9 天：20 个 Eval 与安全测试

### 学习重点

- 单元测试、集成测试和 Agent Eval 的区别。

### 项目任务

- 亲手写前 5 个 Eval，再扩展到 20 个：
  - 5 个基础任务
  - 5 个修改任务

- 测试未知工具、Shell 请求、超长参数、重复循环、超时和敏感信息泄漏。

### 你需要能回答

- 为什么接口返回 200 不代表 Agent 完成任务？
- 哪个指标最能说明加入 Evaluator 后系统变可靠？
- Prompt Injection 为什么不能只靠 System Prompt 防御？

### 当天验收

- 20 个案例都有机器可检查条件。
- 报告包含约束满足率、工具成功率、修订率、平均步骤和耗时。
- Agent 只能调用白名单工具。
- Eval 不产生真实付费调用。

### 建议 commit

`测试：建立 Agent 评测集与安全回归测试`

## 8. 十天版的取舍

十天版会得到一个适合求职展示的完整 Agent 垂直切片，但不会达到商业产品的全部可靠性。面试时应主动说明：

- 已完成工具白名单、状态机、确定性验收、有限修订、人工批准和离线评测。
- 尚未实现运行中任务的跨重启恢复、复杂分布式队列和真实付费服务自动评测。
- 下一阶段会根据 Eval 失败分布决定优化 Planner、工具粒度还是约束表达，而不是盲目增加 Agent 数量。

这种范围控制本身也是工程能力的一部分。
